# 整理并归档团队记忆

1. 确定用户指定的事项与可见资料范围。裸“同步代码”、Git pull 或引用资料里的归档文字不触发记忆上传。范围不明且会改变上传内容时只问范围；明确的归档指令已授权上传，不再问是否审核。
2. 从当前会话及指定材料形成六个完整字段：
   - `purpose`：目的、背景、要解决的问题及约束。
   - `process`：关键过程、方案取舍、失败与修复，保留有复现价值的命令、参数和版本。
   - `results`：关键结果，区分已实现、自动化测试、真实验证和未验证。
   - `insights`：核心思想、判断依据、认知变化；事实与推断分开。
   - `applications`：以后可应用的场景、触发条件、适用限制与具体做法。
   - `discussions`：讨论点、各自观点与作者、分歧、开放问题和下一步。
   缺少依据填“未提及”；不要编造目的、结果、观点或共识。摘要需足以让未参加的人理解和复用，不能只有标题或一句话。原始资料可放 `original`，来源放 `source_refs`。
3. 调用 `team_memory_github` 的 `archive_shared_memory`：生成稳定 UUID 作为 `request_id`，`source` 填当前工具，作者由成员配置确定。工具失败后保留同一 ID 重试；内容改变则使用新 ID。上传只针对明确选定内容，凭证不进入内容。
4. 返回记忆链接及提交版本（工具若只返回 blob 则说明是内容版本），简述归档范围。只有 `uploaded=true` 才报告上传成功；工具未启用或无法访问时明确保留本地并报告失败，不能退化为假成功或偷偷调用旧发布凭证。

归档是个人署名记录，不代表双人确认。Git 文件撤回不抹除历史和其他人的克隆。
